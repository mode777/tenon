# nsx-explore

Read `references/rules.md`, `specs/project.md`, `specs/tech-stack.md`, `specs/memory.md`, then relevant baseline specs and code.

1. Research repository facts yourself; cite paths. Interview one decision at a time, with a recommendation. Challenge assumptions.
2. Add only confirmed facts to baseline specs. Derive requirements from stakeholder goals, not code branches; create module specs only for cohesive blocks with a meaningful interface and significant concern, complexity, risk or decision. Use `assets/feature.md` or `assets/module.md`; do not overwrite settled content. Keep unknowns explicit.
3. Keep proposed or future behaviour out of baseline requirements and architecture. Do not edit code or create a change plan.
4. Surface contradictions for resolution; do not guess. Continue until the intended outcome, boundaries and open decisions are clear.
5. Recommend `/nsx-change` for one deliverable, `/nsx-multi` for staged work or `/nsx-bugfix` for a defect. Switch only with the user's consent. Summarize confirmed findings and unresolved questions.
